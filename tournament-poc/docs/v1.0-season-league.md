## 1. 運営の流れ

| 段階 | 主催者の操作 | 画面 |
| --- | --- | --- |
| 作成 | ホームの「期制リーグ（昇降格・入替戦）を作成」。名前・ルール・総当たりの回数（1 回 / 2 回）・勝ち点・**ディビジョン数の境目・各部の目標人数・定員** | 運営画面のホーム |
| 1 期目 | 選手を登録 → 「組み合わせ」で全員参加 → 対戦カード（全員 1 つのリーグで総当たり）→ 結果 | 既存の各タブ |
| 次期の配置 | 「期・昇降格」タブ →「次期の配置をプレビュー」→ 必要なら修正（所属・不参加・復帰・新規参加・表示名。所属を変えるときは理由が必須）→「プレビューを更新」→「確定して第 n 期を作成」 | 「期・昇降格」タブ |
| 2 期目以降 | 対戦カード（ディビジョンごと）→ 結果 →「入替戦を組む」→ 入替戦の結果（「試合結果」タブ。不戦勝・棄権・延期・訂正も他の試合と同じ）→ 次期の配置 | 既存の各タブ・「期・昇降格」タブ |
| 前期の訂正 | 次期を作った後に前期の結果を直すと、次期の「期・昇降格」タブに違いを表示。反映（対戦カードのないディビジョンだけ）か、記録として承認 | 次期の「期・昇降格」タブ |
| 既存のリーグ大会 | リーグの段階だけの大会は「期・昇降格」タブの「期制リーグにする」で期にできる（移行） | 「期・昇降格」タブ |

既存の「リーグ → プレーオフ」（リーグ上位の決勝トーナメント）とは別の機能です。既存の 10 形式・作成欄の並び・各形式の挙動は変えていません。

### 1.1 主催者が決める人数の境目（アプリの既定の境目はない）

| 設定 | 意味 | 空欄のとき |
| --- | --- | --- |
| ディビジョン数の境目 `thresholds` | 「n 人以上で 2 部制、m 人以上で 3 部制…」を小さい順に（例: `12, 30`） | 人数によらず 1 ディビジョン（昇降格・入替戦なし） |
| 各部の目標人数 `targets` | 1 部・2 部…の人数。最下位の部は常に残りの人数 | 残りを均等に分ける。割り切れない端数は**下の部から** 1 人ずつ多くする（上に配ると、降格した選手が端数で上に戻るため） |
| 各部の定員 `capacities` | 超える配置は確定できない | 定員なし |

境目・目標人数・定員は作成後も「期・昇降格」タブで変えられます（主催者・管理者）。変えるとプレビューの版が変わるため、古いプレビューでは確定できません。

### 1.2 昇降格・入替戦の規則（依頼の仕様どおり）

隣接する上位 A・下位 B: B の 1 位は A へ自動昇格、A の最下位は B へ自動降格、A の下から 2 位と B の 2 位が入替戦（A 側が勝てば両者残留、B 側が勝てば入れ替わり）。最上位の上・最下位の下には作らない。1 ディビジョンなら昇降格・入替戦は作らない。

**人数による成り立ち**: 最上位・最下位の部は 2 人以上、中間の部は 4 人以上（1・2 位と下から 2 位・最下位が重ならない）。満たさないディビジョンは「対象が重なる」として役割を付けず、次期の所属を手動で決めるまで確定しない。次期の配置も同じ最少人数を満たさなければ確定しない（主催者に配置・境目・目標人数の見直しを求める）。

**同順位**: 役割（自動昇格・入替戦・降格・残留）が分かれる同順位の塊、または次期のディビジョンの境目にかかる同順位があれば、その期の「組み合わせ」タブで主催者が順位を手動で決めるまで、入替戦を組まない・次期を確定しない（名前順などで自動では決めない）。

### 1.3 次期の配置の計算（`admin/src/server/04g_season.js`。画面から独立した純粋な関数）

1. 今期の順位表から各選手の役割を決め、入替戦の結果で移動先（基準の部）を決める。
2. 梯子（全員の並び）を作る: 部ごとに「上から降りてきた選手 → 残留（順位順）→ 下から上がってきた選手」。1 ディビジョンの期は順位どおり。
3. 不参加を除き、復帰・新規参加を最後に足す（最下位の部。変えるときは手動）。
4. 次期の人数から境目でディビジョン数を決め、目標人数で梯子を上から区切る。
5. 手動の修正（理由必須）を当てはめ、最少人数・定員・同じ表示名を確かめる。

各行に、前期の所属・順位・昇降格の種類・自動の所属・新しい所属と理由（「1期目 5位のため 2部（5〜8位が 2部）」「入替戦に負けて降格」「ディビジョン増設（次期 17 人 → 3 部制）により 3部」「人数調整（目標人数・欠員）のため 1部 へ繰り上げ」「手動で 1部（理由）」など）を出します。

## 2. データ（スキーマ v4。追加だけ・値の移し替えなし）

| シート / 列 | 内容 |
| --- | --- |
| `Leagues`（新規） | `league_id`（`LGS-…`）・名前・設定（境目・目標人数・定員・回数・勝ち点・ルール） |
| `LeagueSeasons`（新規） | 期ごとに 1 行: `league_id`・期の番号・大会 ID・前期の大会 ID・**確定の記録**（`plan_json`: 根拠の版、前期の所属・順位・昇降格・入替戦の結果と確定時刻・新しい所属・理由・手動の修正・照合の記録）・確定の日時と操作者。確定の記録は 1 セルの上限（50,000 文字）を超えないよう 40,000 文字ごとに `plan_json`〜`plan_json_08` へ分ける（最大 320,000 文字。超えるときはどのシートにも書く前に TOO_LARGE で止める） |
| `LeagueMembers`（新規） | 会員（期をまたぐ選手の ID `LMB-…`）・表示名（最新の期の名前）・状態（参加中 / 脱退）・参加した期・名前の履歴 |
| `Players.member_id`（列の追加） | その期の選手が指す会員。期制リーグでない大会は空欄 |
| 段階の種類 `promotion` | 入替戦。隣接する部の組ごとにグループ 1 つ・試合 1 つ |

**期 = 独立した大会**（Events の 1 行）なので、結果・順位・閲覧ページの URL（`?event=EVT-…`）・公開 / 非公開・削除・CSV・JSON の保存は期ごとに今までどおりです。

### 2.1 期をまたぐ同一人物（名前に依存しない）

- 期の大会に選手が加わると（登録・CSV 取込・旧版で足した選手も）、操作の後に**選手ごとに新しい会員 ID** を付ける。名前が同じ別の会員・以前の期の選手とは結び付けない。
- 次期は会員 ID で作る（表示名を変えても同じ会員。同姓同名は別の会員で、同じ期に同じ表示名は置けないのでプレビューで区別を求める）。
- 脱退（不参加）→ 状態 `left`。後の期で「復帰」を選ぶと同じ会員 ID のまま戻る。期の途中で戻った人は、主催者が「付け替え」で以前の会員 ID に結び付ける（明示的な操作だけ）。
- 既存の大会の複製（F12）・JSON からの復元（F21）は会員 ID を写さない（複製は期の連結にならない。依頼のとおり）。
- **移行**: 既存のリーグ大会は「期制リーグにする」で期にできる（選手ごとに新しい会員 ID）。別々に運営していた過去の大会どうしを後から結び付ける機能はない（名前での自動の対応付けをしないため。必要なら付け替えで個別に結ぶ）。

### 2.2 権限（サーバーで確認。既存の大会ごとの権限に従う）

| 操作 | 主催者 | 管理者 | 共同主催者 | 管理パスワード（スタッフ） |
| --- | --- | --- | --- | --- |
| 入替戦を組む・消す、プレビュー、結果の入力 | ○ | ○ | ○ | ○ |
| 期制リーグの設定・次期の作成・訂正の照合・会員の付け替え・移行 | ○ | ○ | × | × |

- 次期の主催者は前期の主催者（同じ Google アカウント）。管理者が作っても主催者は変わらない。**共同主催者・管理パスワードは引き継がない**（必要なら次期で改めて追加）。
- 送られた大会 ID・会員 ID・選手 ID・前期 / 次期の ID は、その期制リーグ・その大会のものかをサーバーで確かめる（他人の大会は「見つからない」、他の期制リーグの会員 ID は拒否。`tests/v10-season.test.mjs`「権限」）。

### 2.3 確定の二重送信・再試行

- 同じ requestId の再送: 既存の仕組み（10 分）で同じ結果を返す。
- 別の画面・別の requestId: 期の行に「前期の大会 ID」が既にあれば、その次期を返すだけ（2 つ作らない）。
- 古いプレビュー: プレビューの版（根拠・修正・設定の要約）が今の計算と違えば確定しない（`CONFLICT`）。
- 書き込みの途中で止まった場合: 期の行を大会の行より先に書く。期の行だけが残っていたら、次の確定で途中まで書いた行を消して作り直す。

### 2.4 結果の撤回・訂正

- 入替戦を組んだ後にリーグの結果が変わり対戦者が順位と合わなくなったら、プレビューに問題として出し、「組み直す」（入替戦に結果が入っていなければ）を求める。
- 入替戦の結果を「未開始に戻す」と、プレビューは「結果待ち」になり確定できない。
- 次期を作った後に前期の結果が変わったら、**次期の所属は書き換えない**。次期（と前期）の画面に違いを出し、主催者が「反映」（そのディビジョンに対戦カードがないときだけ。試合が始まっていたら不可）か「記録として承認」（理由必須）を選ぶ。記録は確定の記録（`plan_json.log`）と履歴に残る。

## 3. 公開データ

### 3.1 公開する項目（`tests/v10-public.test.mjs` で許可リストを固定）

- 期の一覧（期の番号と、**公開中の期だけ**大会 ID）・期制リーグの名前
- 順位表の昇降格の帯（`zone`: 昇格圏・入替戦・降格圏。規則から決まるもの）
- 入替戦の対戦・結果・組んだ時の順位（「1部 5位」）
- 次期を確定した後の結果（選手ごとに昇降格の種類と次期の部の名前だけ。**理由・手動の修正の理由・会員 ID・確定した人は出さない**）

前後の期の公開・名前の変更、次期の確定・照合のときは、同じ期制リーグの他の期の公開データも作り直します。

### 3.2 試合の多い大会の分割（v1.0）

| 方式 | 内容 |
| --- | --- |
| 上限内の大会 | 今までと同じ出力（版も同じ）。既存の大会の公開データは変わらない |
| 上限（40 万文字）を超える大会 | ロビン・リーグ・スイス式のグループの試合一覧を、回戦の途中で区切らずに約 6 万文字ずつの**パート**（`PublicSnapshots` の行 `EVT-….P01`…）へ圧縮して移す。本体には各グループの `matchesInParts`・`matchCount` とパートの一覧（ID・版）を入れる |
| 閲覧者用アプリ | `?format=json&event=EVT-…&part=EVT-….P01`。**公開中の本体が一覧に載せているパートだけ**を返す（消し忘れた行・非公開の大会のパートは返さない）。一覧（ポータル）にパートは出ない |
| 閲覧ページ | 本体を取り、手元にない・版が変わったパートだけを取って、元の形（従来の公開データと同じ）に戻してから描く。版が合わなければ失敗として自動更新が再試行する。60 試合を超えるグループは節を選んで表示（既定は未確定の試合がある最初の節） |
| 上限 | 1 行の上限（40 万文字）は変えていない。パートは 1 大会 40 個まで。トーナメントなど分割しない段階で本体が上限を超えるときは、今までどおり保存しない（`TOO_LARGE`） |

旧版の閲覧者用アプリ（v0.9.0）は `EVT-….P01` の行を読まないので、ロールバックしても壊れません（試合一覧のない本体だけを表示。§6）。

## 4. 50 人の検証（模擬環境）

`tests/v10-scale.test.mjs`（`npm test` に含む）と `e2e/v10-season.spec.mjs`（閲覧ページ）。結果は「名前順 = 成績順」で 3-0〜3-2 を混ぜて入力。

| 項目 | 1 回総当たり | 2 回総当たり |
| --- | --- | --- |
| 試合数（生成） | 1,225（140 ms） | 2,450（229 ms） |
| 結果の保存（まとめて確定 64 試合ずつ） | 20 回・合計 3.4 秒・最大 195 ms / 回 | 39 回・合計 13.4 秒・最大 506 ms / 回 |
| 順位（運営画面の詳細の取得） | 108 ms・応答 1,595,671 文字 | 246 ms・応答 3,119,905 文字 |
| 公開データ（分割しない場合） | 680,330 文字（上限超過） | 1,325,012 文字（上限超過） |
| 公開データ（分割後） | 本体 39,532 文字 + パート 2 個（60,147・8,698）= 108,377 文字 | 本体 40,038 文字 + パート 3 個（60,147・60,070・18,687）= 178,942 文字 |
| 閲覧ページでの復元 | 分割前と一致（`deepEqual`）・14 ms | 一致・24 ms |
| 次期のプレビュー / 確定（50 人 → 3 部制 16・17・17 人） | 62 ms / 110 ms | 132 ms / 233 ms |
| スプレッドシートのセル数（全シート） | 51,280 | 99,070 |
| 閲覧ページ（Chromium・ローカル。2,450 試合のうち 1,225 確定） | — | 表示まで約 0.38〜0.39 秒・節の切り替え約 0.1 秒・DOM 約 820 要素・初回の取得は本体 + パート 3 個、変化がなければパートは取り直さない |

**開始時（現行コード）は 1,225 試合で 639,067 文字・2,450 試合で 1,244,217 文字（結果なし）となり、公開に切り替える操作自体が保存されなかった**（`docs/v1.0-work.md`）。分割で、50 人の 1 回・2 回総当たりを公開できることを模擬環境で確認しました。

**模擬環境では確かめられないこと（未検証）**: Apps Script・スプレッドシートの実環境での処理時間（1 操作で全シートを読むため、2,450 試合の Matches は約 7.4 万セル。結果の保存 1 回あたり数秒になる可能性）・6 分の実行時間の上限・CacheService の容量（パートは 1 個あたり 3 つ前後のキャッシュ値）・運営画面の詳細の応答（約 3.1M 文字）の通信時間・実機（iPhone・Android）の表示。50 人対応は**模擬環境では合格・実環境では未検証**です。

## 7. 本番に移す前の手順（利用者が行う。このセッションでは行っていない）

1. **自動反映を止める**: リポジトリの Variables `TOURNAMENT_DEPLOY_ENABLED` を `true` 以外に（このままマージすると、その場で反映・移行が走る）。
2. **バックアップ**: スプレッドシート「Tournament PoC」をドライブで「コピーを作成」（共有しない）。
3. **Google 側の設定**: 変更なし（スコープ・スクリプト プロパティ・OAuth クライアント・公開設定は同じ）。
4. マージ → Actions「Tournament deploy」を mode `dry-run` → Summary で前の版番号（運営用・閲覧者用）を控える。
5. 利用の少ない時間に mode `deploy`（運営用 GAS → `migrateStorage`（v3 → v4。シート 3 つと列 1 つの追加・`bak-s3-…` のバックアップ）→ 閲覧者用 GAS → Pages）。
6. **手動の確認**（自分のアカウント・検証用の大会で）: (a) 既存の大会が以前どおり開け、閲覧ページも同じ、(b) 期制リーグを作り 6〜8 人で 1 期目 → プレビュー → 確定、(c) 2 期目の入替戦 → 3 期目、(d) 閲覧ページで期の一覧・昇降格の列、(e) 試合の多い大会（30 人以上の総当たり）を公開して閲覧ページの節の選択、(f) 結果の保存・詳細の取得にかかる時間（実環境の値を `docs/test-plan.md` に記録）。
7. 確認後、`TOURNAMENT_DEPLOY_ENABLED` を `true` に戻す。
8. **戻す**: mode `rollback` に 4 の版番号（§6 の境界）。Pages は閲覧リポジトリの `deploy: …` を revert。シートは戻さなくてよい（追加のシート・列は旧版が無視する。必要なら `bak-s3-…` から）。

## 8. 既知の制約・未検証

- 実環境（Apps Script・スプレッドシート・GitHub Pages）では一度も動かしていない（このセッションは本番・Google に接続していない）。50 人の処理時間・キャッシュ・応答の大きさは**実環境では未検証**。
