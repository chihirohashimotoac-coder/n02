## 3. 選んだ方式と、採らなかった案

### 3.1 識別

- **権限の正本は sub。** `Events.owner_sub`、`Collaborators.sub`（スキーマ v3 の列）。`owner_email` は表示と紐付けの手がかりとして残す。
- **紐付けの記録**（`owner_link_json`・`link_json`）に、紐付けた時のメールアドレス・方法（`created` / `email` / `approved`）・時刻を残す。`owner_email` が記録と違えば（旧版での付け替え・シートの手作業での変更）、紐付けは古いとみなして権限を与えない。
- **紐付けの条件**（`02b_identity.js` の `linkCandidates_`）: ログインで確かめたメールアドレスが一致し、かつ
  1. Google が持ち主を保証できる（`@gmail.com`、または `hd` あり）、かつ
  2. 既に紐付いた (sub, アドレス) の組と矛盾しない（そのアドレスが別の sub に、またはその sub が別のアドレスに紐付いていない）
  なら本人のログインで自動的に紐付ける。満たさなければ「確認待ちのログイン」を記録するだけ（権限なし）で、**共同主催者は主催者が、主催者は管理者が承認**する。承認の画面には sub を出さず、見分け用の参照（sub のハッシュの先頭 12 文字）とログインの日時だけを出す。
- **同じ sub が競合する記録に結び付かないように**: 条件 2 で、1 つの sub が複数のアドレス、1 つのアドレスが複数の sub に自動で結び付くことを防ぐ。確認待ちは 1 件あたり最大 5 アカウント。

採らなかった案:

| 案 | 理由 |
| --- | --- |
| メールアドレスが一致すれば紐付ける（すべてのアドレス） | T1 をそのまま残す |
| 既存の大会の sub を推測で埋める | v0.8.0 までは sub をどこにも記録していない（セッションはキャッシュだけ・履歴はメール）。推測できない |
| 利用者の一覧のシート（sub ↔ メール）を新設 | ログインしただけの人のメールアドレスまで保存することになる。既存の紐付け（大会・共同主催者）から同じ判定ができる |
| 招待メールを送って本人確認 | 新機能（範囲外。メール送信の権限が増える） |
| 管理者の付け替えで、入力したアドレスに即座に権限 | T1・T2 が付け替えの時点で起きる |

### 3.2 ID トークンの確認

- tokeninfo（`GET`）を続ける。`sub` の形式（ASCII 1〜255 文字）を必須にし、`hd` を読む。429・5xx は「Google に接続できない」として扱う。例外の文面はログに出さない。
- 採らなかった案: (a) tokeninfo に `POST` で送る（URL にトークンを載せない）— 公式資料に POST の記載がなく（確認した 2 ページとも GET の形だけ）、本番のログインを壊す恐れがあるため**未採用（未確認）**。(b) Google の公開鍵（JWKS）でサーバー内で署名を確かめる — Apps Script に RSA の署名検証の関数がなく、自前の実装は誤りの危険が大きい。

### 3.3 セッションの保存方式

| 方式 | ポータル ↔ 運営画面の共有・6 時間の復帰 | XSS での盗用 | 構成の変更 | 判断 |
| --- | --- | --- | --- | --- |
| A. 今の localStorage（6 時間） | ○ | 盗める | なし | **採用**（下の改善つき） |
| B. sessionStorage | 同じタブの移動だけ。ブラウザを閉じると消える（店舗端末での開き直しができない） | 盗める | なし | 不採用（要件に合わない） |
| C. HttpOnly の Cookie | ○ | 読めない（ただし XSS からの操作は可能） | GitHub Pages と Apps Script は別オリジンで、Apps Script は Pages 向けの Cookie を発行できない。**同じオリジンのサーバー（独自ドメイン + Cloudflare Workers・Vercel の関数など）が必要**。費用・DNS・デプロイ・CSRF 対策の設計が増える | 不採用（承認なしに構成を変えない。必要なら別途見積もり） |

A に加えた改善: ログアウトは先に端末から消す・サーバーでの無効化の成否を表示・再試行、別タブのログイン・ログアウトを `storage` イベントですぐに反映（運営画面・ポータル）、セッションに sub を結び付け v0.8 形式のセッションは無効、sub をブラウザに渡さない。

残るリスク（未解消。§9）: 同じオリジン（`chihirohashimotoac-coder.github.io`。**同じアカウントの他のリポジトリの Pages も同じオリジン**）で動くスクリプトは `tpoc-google` を読める。運営ページ・ポータルの CSP は `script-src 'self' https://accounts.google.com/gsi/client`（`tools/build.mjs`）で、外部スクリプトは Google のログイン用ライブラリだけ。画面の文字列は `textContent` で入れている。XSS の有無は既存のテスト（選手名に HTML）以上の検査をしておらず、「XSS がない」とは言えない。

## 5. スキーマ v3 と移行

| シート | 追加する列（末尾） | 値の移し替え |
| --- | --- | --- |
| Events | `owner_sub`、`owner_link_json` | なし（空で追加。既存の値は変えない） |
| Collaborators | `invite_email`、`sub`、`link_json` | `email` が入っている行: `invite_email` へ写し、`email` を空にする（旧版に戻しても招待に権限が付かないように） |

移行（`migrateStorage_`）の流れ: 件数を数える → 全シートを同じスプレッドシートに複製（`bak-s2-<時刻>-<シート名>`）→ 列を足す → 値の移し替え（移していない行だけ。何度でも安全）→ 残りがないか確認 → 件数が同じか確認 → `SCHEMA_VERSION` を 3 に。

- 途中で止まった場合: `SCHEMA_VERSION` は 2 のまま（書き込みは止まり、閲覧はできる）。もう一度実行すると続きから終わる（`tests/identity.test.mjs`「移行のやり直し」。同じ秒にやり直してもバックアップの名前が重ならないように修正した）。
- dry-run: 反映の dry-run（`deploy.mjs gas --dry-run`）は移行を実行しない。**移行の値の移し替えそのものの dry-run はない**（件数の確認とバックアップで代替）。本番の Collaborators の行数は、v0.8.0 の反映が 2026-10-26 01:11 UTC のため少数のはず（**未確認**。§8 の手順 2 で数える）。
- 件数・重複の確認: 全シートの件数が移行の前後で同じであること、Collaborators の `email` が空でない未紐付けの行が残っていないこと。重複した大会 ID は従来どおり書き込みを拒否する（`findRecord_`）。

| v0.9 のセッション | v0.8.0 でも使える（メールアドレスを含む） |
| 戻した後にもう一度 v0.9 に進めた | v0.8.0 で付け替えた大会は紐付けが古いとみなし、前の主催者（sub）に権限を残さない。v0.8.0 で追加した共同主催者は招待として扱う |

**境界**: スキーマの移行の後に運営用 GAS を v0.8.0（反映前の版 = Summary に出る「前の版番号」）へ戻すのは、**障害時の一時的な手段**に限る（主催者の判定がメールアドレスだけに戻るため）。戻した場合は、原因を直した v0.9 系を改めて反映して元に戻す。v0.7.1・v0.6.0 へ戻すのは不可（共同主催者の列を知らない版。テストは v0.7.1 で読み書きできることまでを確認）。

v0.9 側での復旧の方法: 紐付けを誤った場合は、管理者が「主催者（管理者のみ）」で正しいアドレスに付け替える（紐付けは外れ、本人のログインと必要なら承認でやり直す）。共同主催者は主催者が解除して招待し直す。移行前の値は `bak-s2-…` のシートにある。

## 8. 本番に移す前の手順（利用者が行う。このセッションでは行っていない）

1. **自動反映を止める**: リポジトリの Variables の `TOURNAMENT_DEPLOY_ENABLED` を `true` 以外にする（このままマージすると、その場で反映・移行・全員の再ログインが起きる）。
2. **バックアップと件数**: スプレッドシート「Tournament PoC」をドライブ上で「コピーを作成」（共有しない）。Events・Collaborators の行数と、Collaborators の `email` 列のアドレスが Gmail・Workspace かを控える（それ以外の人には、反映後に承認が要ることを先に伝える）。
3. **Google 側の設定**: 変更なし（OAuth クライアント・スコープ・スクリプト プロパティ・公開設定は同じ）。
4. マージ → Actions「Tournament deploy」を mode `dry-run` → Summary で前の版番号（運営用・閲覧者用）を控える。
5. 利用の少ない時間に mode `deploy`。全手順が「完了」、運営画面で v0.9.0、`release.json` が今回のコミット。
6. **手動の確認**（自分のアカウント・自分の検証用の大会で）: (a) 運営画面を開くと再ログインを求められる → ログイン →「紐付けました」→ 以前の大会が開ける、(b) ポータルの「作成した大会」が以前と同じ、(c) 管理者画面で各大会に「紐付け待ち」「承認待ち」がないか、(d) 共同主催者のいる大会で、共同主催者がログインして開ける（保証のないアドレスなら承認）、(e) ログアウトで「サーバーでも無効にしました」、(f) スタッフのパスワードで開ける、(g) 閲覧ページ・ポータルの公開一覧が以前と同じ。
7. 確認後、`TOURNAMENT_DEPLOY_ENABLED` を `true` に戻す。
8. **止める・戻す**: 問題があれば mode `rollback` に 4 の前の版番号（§6 の境界に注意）。Pages は閲覧リポジトリの `deploy: …` を revert。シートは戻さなくてよい（必要なら `bak-s2-…` から）。

## 9. 残るリスク・未検証

- セッションの盗用（§3.3）。XSS の不在は未検証。同じアカウントの他の GitHub Pages のリポジトリは同じオリジン（独自ドメインにすれば分けられる。構成の変更なので未実施）。
- 初回の自動紐付けは「信頼の初回利用」: Gmail・Workspace のアドレスでも、v0.8.0 の時代に作られた大会の作成者と、今そのアドレスを持つ人が同じだとは証明できない（Workspace でアドレスが付け替えられていた場合）。管理者の大会一覧で確認できる。
- 確認待ちの承認は、承認する人が本人に確かめる運用に依存する（画面にはログインの日時と識別の参照を出す）。
- tokeninfo の URL にトークンが載る（Google 側でのログの扱いは不明）。
- 実際のスプレッドシートでの移行、Apps Script 上での動作、実機（iPhone・Android）・アプリ内ブラウザ、Safari での `storage` イベントは未検証（Chromium の模擬環境で合格）。
