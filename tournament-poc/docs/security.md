# セキュリティ設計と公開前チェックリスト

## 1. 脅威と対策

| 想定 | 対策 | 確認方法 |
| --- | --- | --- |
| 閲覧者用 URL を知った人が書き込み・初期化を試みる | 閲覧者用は別プロジェクト。書き込み処理がコードに存在せず、OAuth スコープも `spreadsheets.readonly` のみ（読み込みは Sheets API の `values.get`）。呼べる関数は `doGet` `getPublicSnapshot` だけ | 自動テスト `security.test.mjs`・`e2e/security.spec.mjs`（模擬）／実環境 R-07 |
| 運営者用 URL を知った人が操作する | デプロイ設定「アクセスできるユーザー: 自分のみ」で Google 側が遮断。さらに `adminCall` の呼び出しごとに、サーバー側で `Session.getActiveUser()` のメールアドレスを許可リストと照合（取得できない・一致しない場合は拒否） | 自動テスト（模擬）／実環境 R-05・R-06 |
| `google.script.run` で内部関数を直接呼ぶ | 公開関数を 2 つに限定。内部関数は名前の末尾を `_` にしている。**ただし末尾 `_` の非公開扱いには依存しない設計**: 閲覧者用には書き込み関数自体がなく、運営者用は Google 側のアクセス制限で外部から届かない | 自動テスト（関数一覧の固定） |
| 同時更新でデータが壊れる（2 つのタブ、将来の複数運営者） | 書き込みはスクリプトロックで直列化。各行の版番号 `rev` を画面から送り、読み込み後に他で更新されていれば `CONFLICT` で拒否 | 自動テスト（同時更新・ロック取得失敗） |
| ボタン連打・通信再試行による二重登録 | 書き込みごとに `requestId` を付け、サーバーが 10 分間記憶して同じ ID を無視。画面側も実行中は書き込みボタンを無効化 | 自動テスト（二重送信） |
| 不正な入力（型・範囲・Best of 不成立・存在しない ID） | すべてサーバー側で検証してから書き込む（画面側のチェックは補助） | 自動テスト `domain.test.mjs`・`admin-api.test.mjs` |
| スプレッドシートの数式注入（`=IMPORTXML(...)` など） | 先頭が `= + - @` の文字列を拒否。公開データの分割 JSON には先頭に `~` を付けて保存 | 自動テスト |
| XSS（選手名に HTML を入れる） | 画面はすべて `textContent` で表示。`innerHTML` 等を使わないことをテストで固定 | 自動テスト・画面テスト |
| 個人情報・内部情報の公開 | 閲覧者に渡すのは運営者用アプリが組み立てた公開用 JSON のみ（大会名・グループ・選手の表示名・対戦・Leg 数・状態・勝者・更新時刻）。メモ・履歴・操作者メール・版番号は含まない。返却キーの一覧をテストで固定 | 自動テスト |
| 内部エラーの漏えい | 閲覧者用は固定文言（「データを取得できませんでした。」など）のみ返し、詳細はサーバーログへ | 自動テスト |
| 既存の Google ファイルを誤って上書き | 保存先はスクリプト プロパティで指定した 1 ファイルのみ。未初期化のファイルに管理対象外のデータがあれば初期化を中止。シートの削除・既存列の削除はしない | 自動テスト |
| 認証情報の埋め込み | ソースにスプレッドシート ID・メールアドレス・鍵を含めない（ID はスクリプト プロパティ）。テストで検査 | 自動テスト |
| GitHub Pages の閲覧ページ | 静的ファイルのみ（秘密情報なし。`config.js` の URL は閲覧者に配る公開情報）。CSP で通信先を `script.google.com` / `script.googleusercontent.com` に、スクリプトを同じサイトのファイルに限定。`fetch` は Cookie を送らない（`credentials: 'omit'`）。表示は閲覧画面と同じ `textContent` のみ | 自動テスト・画面テスト（Cookie を入れた状態で送られないこと、CSP 違反なし） |
| 埋め込み（クリックジャッキング） | `HtmlService` の X-Frame-Options は既定のまま（他サイトへの埋め込み不可）。n02 からはリンクで開く | — |

## 2. 運営者の認可

```
adminCall(request)
  └ requireAdmin_()
      active  = Session.getActiveUser().getEmail()     … 空なら拒否
      allowed = スクリプト プロパティ ADMIN_EMAILS（カンマ区切り）
                未設定なら [Session.getEffectiveUser().getEmail()]（＝デプロイした本人）
                どちらも取れなければ []（誰も許可しない）
      active が allowed に含まれなければ拒否
```

Google のドキュメントによると、`getActiveUser()` のメールアドレスは「実行ユーザー: 自分」で公開した Web アプリなどでは空になる場合があり、
開発者本人が実行する場合や同じ Google Workspace ドメインの場合は一般に取得できる、とされています
（[Class Session](https://developers.google.com/apps-script/reference/base/session)）。
Phase 1 の構成（自分のみ・本人がアクセス）では本人のメールアドレスが取れる想定ですが、**実環境で未確認**です（実環境 R-04）。
もし本人でも空になる場合は、運営画面に「運営者として認証できませんでした」と表示され、**書き込みは一切できません**（安全側に倒れる）。

## 3. 将来の複数管理者

コードは `ADMIN_EMAILS` による許可リストに対応済みです。ただし、デプロイ方式によってメールアドレスが取得できるかが変わるため、次のいずれかの構成変更が必要です（いずれも未検証）。

| 方式 | 内容 | 注意 |
| --- | --- | --- |
| A. 実行ユーザーを「ウェブアプリにアクセスしているユーザー」にする | 各運営者が自分の権限で実行。`getActiveUser()` が取得できる。アクセスは「Google アカウントを持つ全員」+ `ADMIN_EMAILS` | 各運営者にスプレッドシートの編集権限を共有する必要がある（直接編集は運用上しない） |
| B. Google Workspace のドメイン内に限定 | 「実行: 自分」のまま、アクセスを「ドメイン内の全員」に | 同一ドメインの Workspace が必要（個人の Gmail では不可） |
| C. 本格移行 | 認証・権限管理を持つ別基盤 | Phase 2 以降の検討事項 |

## 4. 公開前チェックリスト

デプロイ後、閲覧者用 URL を配布する前に必ず確認してください。

- [ ] スプレッドシートの共有設定が「制限付き」で、共有相手がいない（Google ドライブの「共有」で確認）
- [ ] 運営者用デプロイ: 実行「自分」、アクセス「**自分のみ**」
- [ ] 閲覧者用デプロイ: 実行「自分」、アクセス「全員」
- [ ] 閲覧者用プロジェクトの `appsscript.json` の `oauthScopes` が `spreadsheets.readonly` の 1 つだけ（承認画面でも参照のみであること）
- [ ] 閲覧者用プロジェクトの「プロジェクトの設定 → スクリプト プロパティ」に `SPREADSHEET_ID` 以外の値がない
- [ ] 運営者用 URL を、ログインしていないブラウザ（シークレット ウィンドウ）で開くと Google のログインまたはアクセス拒否になる（R-05）
- [ ] 運営者用 URL を、別の Google アカウントで開くとアクセスできない（R-06）
- [ ] 閲覧者用 URL を、ログインしていないブラウザで開くと閲覧画面が表示される（R-01）
- [ ] 閲覧画面のブラウザの開発者ツールで `google.script.run.adminCall({})` を実行しても失敗する（R-07。閲覧者用には存在しない関数）
- [ ] 公開している大会が意図したものだけ（運営画面の大会一覧で「公開中」を確認）
- [ ] 選手名に本名を使う場合は、本人の同意があること（PoC ではサンプル名のみを使用）
- [ ] Apps Script プロジェクトの共有相手がいない（プロジェクトの編集者はコードと実行ログを見られるため）
