## 1. 前提（守ること）

  - マージ条件: 最新 main で再現 → 修正 → 必須チェックが最新コミットで成功 → **PR 本文に大会プレビュー URL**、開けること・表示コミットが最新コミットと一致することを確認し、運営・閲覧の該当操作をプレビューで確認 → 権限・競技結果・保存データ・公開範囲に想定外の影響なし → 戻し先（GAS 2 つ・Pages）を把握 → PR に項目・原因・差分・再現・検証・未検証・コミット・プレビュー URL・影響・戻し方。
  - **承認範囲外（止めて利用者に聞く）**: 競技ルールの解釈が要るもの・本番データの一括修復・シート構造の変更。
- **本番配信が失敗したときの再実行は、必ず利用者に確認してから**（このセッションでも確認した。4 を参照）。再実行の前に main が進んでいないことを確かめる（古いコミットで上書きしない確認に引っかからない）。

- **GitHub の読み書きは MCP ツール（`mcp__github__*`）だけ**。`gh` は検索（`gh api -X GET search/...`）だけに使う。本番の照合は GitHub ではない公開の窓口を `curl` で読む（下の 2）。
- **作業ブランチは、そのセッションに指定されたもの**（システムの指示の「Develop on branch …」）。このセッションは `claude/charming-sagan-vzh8ul`（閲覧リポジトリ側も同名が指定されていたが使っていない）。マージ済みの PR のブランチは、最新 main から同じ名前で切り直す（`git checkout -B <branch> origin/main` → `git push --force-with-lease`）。
- 作業ブランチが PR に使われている間に次の監査案を進めるときは、`git worktree add /home/user/n02-prNN origin/main -b local-prNN` で別の場所を作り、`ln -s /home/user/n02/node_modules /home/user/n02-prNN/node_modules` で依存を共有する。前の PR のマージ後に、作業ブランチを main から切り直して `git cherry-pick` で載せる。**片づけ（worktree remove・branch -D）は push・マージを確かめてから別のコマンドで**。消す前に、各ブランチで変えたファイルの中身が main と同じことを `git diff <commit> origin/main -- <files>` で確かめる（cherry-pick し直したコミットは `git cherry` では「+」と出る）。
- **作業ブランチが PR に使われている間は、他の変更をそのブランチに push しない**（上書きになる）。別の作業場所でローカルにコミットしておき、PR のマージ後に載せる（Stop フックが「未コミット」を指摘したときも同じ）。
- PR は Draft で作り、確認が済んだら ready にしてマージ（`merge_method: merge`、`expectedHeadSha` は `git rev-parse HEAD` の 40 桁をそのまま）。
- コミットの末尾・PR 本文の末尾の帰属表示は、そのセッションのシステムの指示に従う（セッション URL はセッションごとに違う）。
- AGENTS.md: 依存は既存のロックファイルどおり `npm ci`（このセッションも開始時にリポジトリ直下で実行。新しいライブラリは入れていない）。

## 2. 確認の道具

前のメモの 2 と同じ（大会プレビューの URL・模擬 API・管理者の鍵・故障の注入・本番の照合・CI・ローカルの試験）。このセッションで分かったこと:

- **Playwright の確認スクリプト**: `require('playwright')` はどこからでも読める。共通部分（管理者の鍵を入れて読み直す・模擬 API を呼ぶ `ok(action, payload)`・大会を一覧の「開く」で開く・タブを押す・トースト・横スクロールの量）をまとめた小さな `common.cjs` を scratchpad に作ると速い（次のセッションには残らない）。
  - 模擬 API の `requestId` は英数字とハイフンだけ（`'pv-' + crypto.randomUUID()`。`Math.random()` の小数点は「requestId がありません」で拒否される）。
  - 同じ URL への `page.goto`（# だけ違う）は読み直さないので、`goto` の後に `page.reload()`。
  - 閲覧ページは同じプレビューの `site/index.html?event=<ID>` で開ける（運営用の模擬で作って `updateEvent` で `isPublic: true` にした大会が出る）。
  - **スマートフォンの確認は `isMobile: true, hasTouch: true, deviceScaleFactor: 2`**（e2e の `mobile` と同じ）。`isMobile` なしの 390px は「PC のブラウザの窓を狭めた」状態で、結果が違うことがある（ダブルエリミの閲覧ページは 38px の横スクロールが出る。5 を参照）。
- **待ち方**: 前景の `sleep` は止められる。配信・プレビューの構築は `run_in_background` の Bash で `until`（`for i in $(seq 1 50); do …; sleep 12; done`）を回し、終わったら通知を受ける。CI は `mcp__claude-code-remote__send_later` で 20〜25 分後に自分へ確認を予約する（CLAUDE.md だけの PR でも CI は 25 分前後かかる）。
- **本番の照合の手順（毎回）**: ① 3 つの `release`（運営用 GAS の匿名 GET・閲覧者用 GAS の `?format=version`・Pages の `release.json`）② 閲覧リポジトリの main の先頭（`deploy: n02 <SHA>`）③ Actions の deploy ジョブのログ（`tail_lines` 140 で「運営用 GAS の更新: 版 X → Y」）④ その PR が変えた公開ファイル（`admin/admin.js`・`viewer-plus.js`・`formats.js` など）に修正が入っているか（コメントの「監査 PR-NN」を `grep -c`）⑤ `config.js` が閲覧者用 GAS を指しているか。
- `mcp__github__create_pull_request` が 502 を返しても PR が作られていることがある。作り直す前に `list_pull_requests`（`head` で絞る）で確かめる。

- **#59（PR-11）の本番配信で、Pages の push が 3 回続けて失敗**（run 41816993047、10:52〜11:12 UTC）。
