## 20 スタッフ認証: 匿名の誤りの試行の影響

コード（`admin/src/server/02_auth.js` の `verifyStaffPassword_`）: 誤りの回数を**大会 ID ごと**に数え（`staff-fail:<大会 ID>`）、10 回で 600 秒受け付けません。数える処理は**スクリプト全体のロック**（`LockService.getScriptLock()`、待ち 10 秒）の中で行います。

模擬で、管理パスワードを設定した大会 A・B を作り、A に匿名で誤ったパスワードを 12 回送った結果:

| 確かめたこと | 結果 |
| --- | --- |
| 1〜10 回目の誤り | `AUTH_INVALID` |
| 11・12 回目 | `AUTH_LOCKED` |
| その後の大会 A の**正しい**パスワード | `AUTH_LOCKED`（拒否） |
| 大会 B の正しいパスワード | 成功（影響なし） |
| 試行の前からログインしていた A のスタッフの結果の保存 | 成功（影響なし） |
| 10 回目から 599 秒後の A の正しいパスワード | `AUTH_LOCKED` |
| 同じく 601 秒後 | 成功 |

分かったこと:

- 公開中の大会 ID（閲覧ページの URL に出る）を知っていれば、誰でも 10 回の誤りで、その大会のスタッフの新しいログインを 10 分止められます。11 回目以降は期限を延ばさないので、止め続けるには 10 分ごとに 10 回送る必要があります。
- すでにログインしているスタッフのセッションには影響しません。
- コードから: 誤りの試行のたびに、スクリプト全体のロックを取ります。そのため大量の試行は、同じ時間帯の運営の保存の BUSY（ロックの待ちの 10 秒切れ）の原因になりえます。模擬では計測できず、本番での計測が要ります。

改善の候補（未着手。総当たりへの強さとログインのしやすさの取り合いなので、決めるのは利用者）:

1. 数える処理をスクリプトのロックから外す（キャッシュの数え方を楽観的にする）。BUSY への影響を断てますが、並列の誤りの数え漏れを少し許すことになります。
2. 締め出しの間も、正しいパスワードは通す。総当たりの回数の上限はなくなるので、代わりに遅延を入れます。
3. 締め出しの時間を短くし、回数の上限を上げる。

## 21 閲覧者用 GAS: 公開されていない ID の連続の全読み込み

コード（`viewer/src/server/00_viewer.js` の `loadEntry_`）: キャッシュにない ID を問い合わせると、スクリプトのロックの中で `PublicSnapshots` シートを**全部**読み直します。公開されていない ID は、その ID だけを 20 秒「なし」としてキャッシュします。

模擬（公開中のサンプル大会 5 件、公開シートは JSON で約 15 万文字）で、0.1 秒ごとに 100 回問い合わせたときに、シートを読んだ回数:

| 問い合わせ | シートを読んだ回数 |
| --- | --- |
| 公開中の同じ ID × 100 | 1 |
| 公開中の 5 つの ID を順に × 100 | 1 |
| 同じ未知 ID × 100 | 1 |
| **毎回違う未知 ID × 100** | **100** |
| 公開中 50 回 ＋ 毎回違う未知 50 回（交互） | 51 |

分かったこと:

- 毎回違う未知の ID を送ると、1 回ごとに公開シートの全部（公開中の全大会の公開データ）をロックの中で読み直します。読み直しのたびに全大会のキャッシュも入れ直すので、公開中の大会の閲覧者は、キャッシュに当たり続けて影響を受けません（交互の行）。ただし、ロックの待ち（3 秒）とシートの読み込みの回数（Google の割り当て）は増えます。
- 改善の候補（未着手）: キャッシュにある「公開中の ID の一覧」（一覧のキャッシュ）に載っていない ID は、シートを読まずに「なし」と答える。応答の形（`NO_PUBLIC_EVENT`）は変えません。新しく公開した直後の大会を「なし」と誤判定しないよう、一覧の版と公開の時刻の扱いを決める必要があります（監査の「キャッシュ誤判定に注意」）。

## 22 閲覧ページ: パートの同時取得の数

コード（`viewer/src/client/viewer.js` の `withParts`）: 本体の取得の後、手元にない・版が変わったパートを**全部同時に**取りに行きます（同時数の上限なし）。パートは大会あたり最大 40 個です（`MAX_SNAPSHOT_PARTS`）。

ローカルの模擬サーバー（`tools/preview-server.mjs`）で、リーグ 1 グループの大会を公開し、閲覧ページを 390×844 で開いたとき:

| 人数（試合数） | パートの数 | 初回の取得（本体 ＋ パート） | 同時の最大 | 初回の表示（パートの応答の遅れ 0 / 300 ms） |
| --- | --- | --- | --- | --- |
| 30 人（435） | 0 | 1 | 1 | 209 / 227 ms |
| 50 人（1,225） | 2 | 3 | 2 | 238 / 916 ms |
| 80 人（3,160） | 3 | 4 | 3 | 221 / 925 ms |
| 110 人（5,995） | 6 | 7 | 5〜6 | 260 / 923 ms |

分かったこと:

- 閲覧者 1 人の初回の取得は「1 ＋ パートの数」回で、パートは同時に送ります。自動更新では、版が変わったパートだけを取り直します。
- QR コードで N 人が同時に開くと、閲覧者用 GAS への同時の要求は最大で N ×（1 ＋ パートの数）本になります。パートの上限 40 に近い大会では、1 人で 41 本になります。
- 表示までの時間は、パートの応答の遅れで決まります（並列なので、パートの数にはあまり比例しない）。
- 改善の候補（未着手）: パートの同時の取得を 3〜4 本までに絞る。要求の山は低くなりますが、パートの多い大会では初回の表示が遅れるので、本番で取得数と初回の表示を測ってから決めます。

## 23 保存の性能: 1 回の保存で読む量

コード（`admin/src/server/03_storage.js` の `ctx.table`）: 操作ごとに、使うシートを**全部**読みます（大会で絞らない）。

模擬で、16 人 1 グループのロビン（120 試合）の結果を 1 試合ずつ 30 回保存したとき、1 回の保存で読んだ文字数（シートの値を JSON にした長さ）:

| ほかの大会の数（サンプル大会） | 読んだ文字数（p50） | そのうち PublicSnapshots | Matches | History | 応答の大きさ |
| --- | --- | --- | --- | --- | --- |
| 0 | 138,850 | 84,363 | 30,185 | 25,476 | 172,201 |
| 10 | 618,870 | 384,653 | 91,525 | 84,526 | 172,201 |
| 40 | 2,058,930 | 1,285,523（62%） | 275,545 | 261,676 | 172,201 |

（History の行数は 36・66・156。1 行あたり約 1,300〜1,700 文字。模擬の処理時間は p50 11 → 20 → 48 ms で、本番の時間の目安にはなりません）

分かったこと:

- 1 回の保存で読む量は、**ほかの大会の数に比例して**増えます。最も大きいのは PublicSnapshots（全大会の公開データ）です。
- History（操作の履歴）も全部読むので、運用を続けるほど保存のたびに読む量が増えます。
- 保存の応答は、大会の詳細の全部を返します（この大会で約 17 万文字）。
- 監査の方針どおり、効果を確かめられたら次の 3 つを別々の PR にします。
  1. 公開データの読み込みを、対象の大会の行だけにする。
  2. 履歴の読み込みを、表示に要る分だけにする。
  3. 保存の応答から重複を減らす。

  どれも、変更の前後で本番の p50/p95・応答の大きさ・BUSY・公開の遅れを比べてからです（応答の形を変える 3 は、運営画面と互換の版の組で戻せるようにします）。
